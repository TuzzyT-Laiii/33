# 大模型训练/开发情境：Acme Seren原生窗口

本版基于PR #36的`6de2e4cde4dbf66f055c0802364c96e511945bbe`，将B/C/D-TRN四档规模的数据源确定为**Acme Seren**。情境名称不变。依赖PR #34的原生窗口与天气链路、PR #36的CPU/基础功率审计；审阅顺序为#34 → #36 → 本PR。INF的#35可按其依赖单独审阅，组合时保留各用途的新输入并重算组合结果。

## 窗口与证据边界

正文采用同期需求可观测且功率监测通过筛选的真实小时。Seren原始作业为818,327行，其中GPU作业450,590条、独立CPU作业367,737条。作业起止UTC 2023-02-28T16:18:54+00:00至2023-08-22T07:01:59+00:00。全作业表保留4,192个小时分组（174.6667个等效日），包括首尾部分小时；窗口不循环、不延长、不年化。

监测日历覆盖UTC **2023-05-16T09:43:15+00:00至2023-08-18T00:00:00+00:00**，约93.595天，涉及2,246个小时分组。按2,288张A100物理库存的报送覆盖至少80%、每小时至少228个15秒采样（95%）、分配量为正且采样中没有库存超额筛选。正文保留**2,057个小时分组**（85.7083个等效日），实际采样2056.9667小时。

正文首小时为**2023-05-16T10:00:00+00:00**，最后小时为**2023-08-17T23:00:00+00:00**。两端之间排除189小时，形成54个连续片段，最长451小时。全部排除小时与原因见[缺口表](body-excluded-hours.csv)，片段见[区间表](body-segments.csv)。缺口不插值、不延续前值、不压缩真实时间；正文电量仅积分保留的小时分组。每小时采样最多允许3分钟缺失，因此小时均值还依赖小时内部缺测的代表性。

本版选择同期合格窗口，是因为每个正文小时都具有同时间的作业分配和功率监测支持。GPU功率仍是**集群条件反推**：报送状态无法确认在线状态，且没有逐作业设备映射。正文不能解释为逐预训练作业功率直接实测。完整作业窗口用于检验更长需求期及任务构成的影响。

## 需求与功率方法

按作业`[start_time,end_time)`与小时的实际交集累计GPU小时、GPU作业宿主CPU核心小时及各任务类型。独立CPU作业单列诊断，保持原Kalos处理方式，不并入TRN功率。GPU需求除以完整作业表瞬时并发峰值**2032张**；同时间事件先合并。该归一化沿用Kalos口径，用于将需求迁移到给定设备规模，区别于反推时采用的2,288张物理库存。

CPU功率仍沿用PR #36：`u_cpu_proxy=0.25×GPU分配份额`及SPECpower平滑曲线。实际宿主CPU分配共39,367,649.34核心小时，独立CPU为210,246.86核心小时，均已输出；它们是分配量，不是CPU实测利用率。由同一GPU比例构造的CPU代理没有另行添加独立CPU业务。

每个15秒时刻采用`P_est=报送GPU平均功率×2288`，再按小时对齐分配与功率。已分配GPU比例为

`r(t)=[P_est(t)−(2288−N_alloc(t))×P_idle]/[N_alloc(t)×400W]`。

默认空闲60W。主方案直接采用同小时`r(t)`，不使用Kalos 271卡日形状，也不使用文献0.80。源设备为A100-SXM 80GB、400W；目标B/C使用H100 PCIe、350W，D使用H100 SXM、700W，已分配GPU功率为`目标GPU数量×分配份额×目标TDP×r(t)`。未分配目标GPU空闲仍为PCIe 50W、SXM 70W。敏感性50/60/70W改变的是**源集群反推的空闲假设**，不同时改变目标设备空闲端点。

按比例跨A100/H100及PCIe/SXM迁移是工程假设，未保持同等吞吐、运行时长或训练进度。各类型同小时共用集群反推比例；任何类型分项功率都是按分配占比分摊的模型值，无法独立标定预训练、MLLM、SFT或评估功率。

### 逐小时比例及日周形状

GPU采样时间加权均值**0.762316**；P10/中位数/P90为**0.613946/0.768276/0.896305**；小时范围0.309131—1.062429。8个小时超过1、无负值，正文保留并标记，截断方案单列。它们也可能反映缺测外推或库存假设误差，不能直接证明板卡持续超过额定TDP。

24个UTC小时分组的GPU时间加权比例峰谷比为**1.031025**，最低UTC12时、最高22时。168个源星期小时分组的峰谷比为**1.175738**，每个分组有9—14个观测小时。按七个星期日汇总的峰谷比为1.064701。这些形状是同期混合负载条件统计，包含作业构成与分配变化，不能归因于检查点或认为它们是稳定的预训练自然日周期。主方案逐小时使用原序列，日周分组仅用于展示。

## 图件、核验与文件

- `figure1-source`：原生分配、功率比例及报送覆盖，缺口保留。
- `figure2-comparison`：B/C/D典型日的IT与设施新旧对比。
- `figure3-shapes-sensitivity`：日周功率形状、D-TRN敏感性及包含MLLM的任务构成。

图件为中文PNG（300dpi）和嵌入字体PDF；程序检查字形覆盖、边界和字体嵌入，按用户规定不调用视觉检查。分组条件均值未提供因果或置信区间解释。

验证已读取并核对696个小时文件、2,055,816条保存小时记录及3,000个汇总行；检查输入哈希、类型GPU/宿主CPU守恒、小时电功率与热平衡、真实日历/缺口、日周汇总及PR #36基础/CPU/设备参数一致。真实旧版全年天气输入复现设施功率，允许缺口的结果与完整序列同小时子集一致，默认接口仍拒绝缺口。

原始作业与GPU监测只留服务器共享卷。Git保存汇总、图件、来源哈希和审计；逐小时IT/设施Parquet留在服务器`results/trn-seren-20261101/hourly/`，其SHA-256见[计算清单](calculation-audit.json)。分析一次只处理一个情境、地点、年份和方案，不合并全量小时数据到内存。没有操作MIT源目录、流式进程或STOP文件。

复算入口为`analysis/launch_trn_seren.sh`；流程为`prepare_trn_seren.py` → `build_trn_seren.py` → `verify_trn_seren.py` → `plot_trn_seren.py` → `report_trn_seren.py`。依赖见`analysis/requirements-trn-seren.txt`。原始数据入口和哈希沿用[PR #36证据审计](../trn-power-model-20261101/job-power-evidence/README.md)，官方来源为[AcmeTrace](https://huggingface.co/datasets/Qinghao/AcmeTrace)。HPC、CLD、SAI、INF及既有历史结果保持各自版本。
