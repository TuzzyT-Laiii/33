## 4. 预训练与RL的技术机理

### 4.1 预训练允许保存后暂停，同步规模会限制调度方式

预训练可以保存checkpoint并退出。保存参数、优化器状态、进度及数据读取状态后，GPU显存可释放，后续重新加载继续训练；恢复质量和顺序仍需核验。仅有模型权重不足以完整恢复训练状态。[PyTorch通用checkpoint说明](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html)、[CheckFreq全文](https://www.usenix.org/system/files/fast21-mohan.pdf)

Meta的Llama 3 405B在16K GPU训练中，54天记录466次中断，包含47次计划中断，仍取得超过90%的有效训练时间；这直接证明大规模预训练能中断后继续。论文还描述同步等待、checkpoint及整作业启动/停止造成数十MW瞬时变化。因此，固定并行配置下每个执行段须同时取得完整GPU组，电力与恢复开销需要同时核算。[Llama 3 §3.3.4](https://arxiv.org/html/2407.21783v3)

本数据中Acme预训练GPU数P50/P90为512/1,024张，实际单次运行中位为635秒，该类含408条取消和49条失败记录；同时，运行≥1小时的预训练占该类GPU小时96.80%。实际历史段长不能解释为软件最短连续运行时间，也不能从频繁取消推导低成本恢复。

运行中减少卡数需要重新分片、修改并行配置并维持统计效率；普通固定世界大小训练没有“抽走一半GPU仍按原速度运行”的依据。Pollux展示了支持弹性训练的软件和goodput模型，其能力必须在对应应用中实现和校准。[Pollux，OSDI 2021](https://www.usenix.org/system/files/osdi21-qiao.pdf)

### 4.2 RL/RLHF有阶段边界，阶段波动不会自动释放资源

以PPO式RLHF为例，actor生成rollout，随后计算reward/reference/critic输出，再训练actor与critic。阶段的计算、通信和显存需求不同，可能形成等待和功率波动；actor/critic还需要梯度和优化器状态，多模型共同驻留可能增加显存压力。算法变化会改变模型数量，例如并非所有RL方法都保留critic。[HybridFlow §2](https://arxiv.org/html/2409.19256v2)

ReaL（ReaLHF系统）通过参数重分配在模型函数之间改变GPU布局，说明阶段间重新组织资源具有技术可行性；该系统仍区分持续驻留的梯度/优化器状态与可转移的活动状态。阶段结束、显存卸载、退出工作进程和调度器归还GPU分别需要实现；当前作业日志没有这些控制信息。[ReaL §4–6](https://arxiv.org/html/2406.14088v2)

若要暂停RL实验，应根据具体算法保存多模型和优化器、训练进度、采样状态及未完成数据；可能还包括环境或buffer状态。这是恢复验收清单，不能由一个RL标签推定全部满足。四来源无法提供RL条数、RL GPU小时、rollout/learning占比或阶段卸载成功率，均须标成**数据无此字段，需外部假设或新增观测**。

### 6.1 连续段相对小时尺度的意义

令`L`为本段有效计算分钟，`H`为该段阻塞保存、恢复和额外重算分钟之和。开销占比限制`H/(L+H)≤ε`，故`L≥(1−ε)H/ε`。在ε=5%的研究情境下：

| 每段总开销H（假设） | 最短有效计算L | 最短完整占用L+H | 若只允许整小时占用，向上取整 |
| ---: | ---: | ---: | ---: |
| 1分钟 | 19分钟 | 20分钟 | 1小时 |
| 5分钟 | 95分钟 | 100分钟 | 2小时 |
| 10分钟 | 190分钟 | 200分钟 | 4小时 |
| 30分钟 | 570分钟 | 600分钟 | 10小时 |

该推导约束的是重复执行段。还需增加等待下一个合法checkpoint的时间、重新获得完整gang的等待及实际截止时间；它们不能全部用一项固定恢复分钟数替代。若整段仅能占用1小时、开销容忍5%，则H最多3分钟。`checkpoint-sensitivity.csv`还包含ε=1%和10%的敏感性；所有数字均为假设推导，未冒充当前集群实测。

### 6.2 大量一分钟以内作业的小时柔性含义

Eval有效记录中有10,658条少于60秒，占57.7075%，却只占Eval自身GPU小时2.5109%，约占全部GPU小时0.005845%。Debug少于60秒的102条，占其条数18.9944%、GPU小时1.1413%。独立CPU有41,360条少于60秒，占97.3039%，资源小时占比为8.9189%。

因此，短任务可通过批量改变启动顺序形成小时移峰，但应整体运行，并保留到达、依赖、期限和峰值并发。把中位44秒的Eval逐条扩成1小时会把该时长放大约81.8倍；CPU的8秒扩成1小时为450倍。大量短任务的条数不能作为可移峰电量比例，也不能为预训练剩余95.55%的GPU小时提供柔性证据。

统计采用精确区间交集：`W_h=Σ_i n_i×|[s_i,e_i)∩[h,h+1h)|/3600`。建议在任务层安排非抢占作业或合法checkpoint段，再积分到小时供能模型；小时能源变量本身不足以证明执行日程可行。对ASI，缺少细粒度跨度时只能做明确标注的聚合条件情境。

当前[八城市模型](../eight-city-flex-value-20261029/README.md)把动态IT电量作为可分割工作量，明确尚未加入作业连续性和checkpoint开销。本报告提供后续加入这些约束的依据，不修改或重启其求解任务。类型GPU小时份额只有在逐类、逐硬件的功率与有效服务量映射成立后，才能转换为该模型的`φ_t`；不能直接以22.7384%替换全设施功率柔性比例。当前按执行曲线形成的小时工作量也不能恢复任务真实到达时刻；使用历史完成时间作deadline同样属于研究假设。
