# TRN 原生90天窗口与 Acme GPU 功率形状

本次继续更新 PR [#36](https://github.com/TuzzyT-Laiii/33/pull/36)。B/C/D-TRN 各四档规模保留一次 UTC 2023-05-18 00:00 至 2023-08-15 23:00 的 **2,160小时**需求。气象按源月日小时对应参考网格2025及八城市2023—2025，共25个地点×气象年；没有循环成全年，也没有换算年电量。

**中央方案将固定设备样本的集群日形状迁移到0.80中央水平。该形状是工程情境；公开数据无法识别完整的已分配GPU功率序列，也无法识别预训练专属的日周期。** 直接采用已分配GPU实测比例的方案(b)缺少合格标定小时，因此不产生该方案的H100曲线。

## Kalos 监测与分配反推

硬件为 [Acme NSDI 2024论文](https://www.usenix.org/system/files/nsdi24-hu.pdf)所述的302个八卡节点，共 **2,416张A100-SXM 80GB、每卡TDP 400W**。官方[作业表](https://github.com/InternLM/AcmeTrace/tree/6d6ac9cd15f3b01151ac6ba00ecddd9156f0dc73/data/job_trace)与[完整监测](https://huggingface.co/datasets/Qinghao/AcmeTrace)版本及原件SHA-256沿用父目录获取审计；两份功率/利用率原件再次核对哈希。

发布表有 **2,344个设备列**，各时刻非空列数只能称为报送设备数，无法确认未报送设备是否在线。监测与整个作业表重叠 **33个小时分组**；与90天窗口仅重叠 **16.4958个采样小时**、17个小时分组。原生重叠期报送覆盖率仅 **11.45%—35.84%**；作业表全部重叠期为 **11.45%—48.22%**。

功率与利用率各自的有效设备总体也不同。原生重叠期，同设备同采样时刻两项同时有效的覆盖率仅 **1.77%—13.49%**。小时表分别保存功率、利用率及配对计数；不将两种全体均值当作同一批设备的联合观测。

分配量取全部GPU作业的半开区间 `[start_time,end_time)`，按精确15秒采样时刻计算，并另给出小时区间积分、预训练分配量、作业启动/结束数量及卡数。三条 `RUNNING` 记录缺少结束时间，其中一条预训练占用1,024卡；`submit_time + duration` 给出的导出时刻相差仅1秒，因此积分到该右删失时刻，不延长到未观测未来。`duration`包含排队，不能直接当作执行时长。目标需求仍沿用#34冻结的原生序列；该序列没有纳入这三条删失记录，校准分配量与目标需求的差异单独保留。

同设备同采样时刻的零GPU利用率功率代理均值为 **68.127W**，1W直方图中位数为 **64.5W**，共480,702个样本。缺少设备分配映射，零利用率仍可能发生在已分配但等待的GPU，无法证明这些样本属于未分配状态。中央反推用论文约60W，另列50W、70W及该实测代理敏感性。

若已知同一总体的在线设备数，应使用 `p_alloc=[P_cluster−(N_online−N_alloc)×P_idle]/N_alloc`。本数据中报送数经常小于全群分配数，二者不可直接相减。本次另外审计代表性假设下的估计：每个采样时刻先用有效设备功率均值乘2,416，再与全群分配量和未分配空闲功率平衡。该估计要求缺测设备与报送设备具有相同功率分布；当前低覆盖数据无法支持这一条件。

原始监测包含超过400W的样本，TDP也不构成绝对瞬时功率上限；这些观测均保留。0—1作为本轮目标小时情境的范围约束。无法标定的主要原因是重叠覆盖不足和分配/监测总体关系未知。右删失作业的导出时刻不计为实际完成事件。

以60W空闲计算，原生重叠期正分配小时的反推比值范围为 **0.956—1.655**，P10/中位数/P90为 **1.279/1.310/1.330**。这是带代表性假设的诊断分布，不作为训练功率分布。仅1个小时落在0—1；要求报送覆盖至少80%、时间采样至少95%且功率在0—TDP后，合格小时为 **0**。原始反推值与筛选标记均保留。50/60/70W及零利用率代理的完整结果见 [反推敏感性](inverse-sensitivity.csv)。

## 形状迁移及敏感性

采用全部Kalos发布监测，选择在至少99%有效发布时刻均有功率记录的固定设备集合，共 **271张GPU**。先对每张设备求各UTC小时的样本均值，再对固定集合等权平均。这样控制报送设备逐步加入带来的组成变化；时间缺口不延续前值，发布窗口以外没有监测支持。

固定样本的小时均值为 **181.003—208.284W**，日内最高/最低为 **1.1507**，最低UTC **13时**、最高UTC **20时**（北京时间分别加8小时）。这些数值包括固定集合中的空闲和混合业务，设备集合也不保证代表全群或预训练。

`r_target(h)=0.80×s(h)/weighted_mean[s(h)]`，权重为90天原生需求中各小时的GPU分配量。目标比例范围 **0.7298—0.8398**，GPU小时加权均值严格为 **0.8000**。这是将观测到的集群形状用作训练情境的假设；90天需求没有重放，24小时功率因子在其中重复使用。没有加入未获支持的星期修正。

目标B/C为350W H100 PCIe，D为700W H100 SXM；0.80中央水平继续使用父报告的H100训练文献情境依据。A100固定集合同时包含分配变化、等待和运行状态，不能分离这些成分；将其形状作用于目标已分配功率可能重复计入部分需求变化，因此同时给出幅度0及设备集合敏感性。

敏感性包括固定集合覆盖阈值95%/99%/99.9%，以及日形状幅度0、0.5、1、1.5倍。每种形状都保留0.80的GPU小时加权中央水平并检查比例在0—1，未用TDP截断改变原始观测。原有0.65/0.80/0.95训练水平敏感性保留在父目录历史审计中。

全部监测的周内分组及样本数见 [周内描述统计](kalos-observed-weekly.csv)。窗口短、周重复次数有限且报送设备组成变化，不能识别稳定周内规律。目标曲线的周内峰谷比来自原生分配与每日迁移因子的共同作用。作业启停与监测功率可以按时间并列；缺少设备映射、检查点和同步事件日志，不将同时变化解释为检查点或作业启停的因果效应。

## 验证与复算

本次完成 **12个TRN情境×25个地点气象年×7个功率方案**，共4,536,000行小时结果。逐份核对输入哈希、2,160小时原生顺序、冻结需求/天气/服务器数量、独立GPU公式、IT分项、设施及热平衡守恒。新增参数未改变原有静态调用结果，SAI/INF没有新增修改。

复算顺序为 `aggregate_trn_acme_hourly.py` → `prepare_trn_diurnal.py` → `build_trn_diurnal.py` → `verify_trn_diurnal.py` → `report_trn_diurnal.py` / `plot_trn_diurnal.py`。原件目录为服务器共享卷 `data/raw/trn-power-model-20261101/`，小时结果及本报告目录为 `results/trn-power-model-20261101/diurnal-acme/`；输入原生小时表位于 `results/typical-load-curves-20261101-v3-native/` 和对应 `data/processed/`。所有输出都受SHA-256审计。

本轮结果依赖#34的原生窗口改动。审阅顺序为#34原生窗口、#36功率模型与本次TRN迁移形状；#35仍处理INF日内变化，组合时保留其INF方法并应用#36的CPU曲线，重新计算组合产物。本次没有合并PR或启用自动合并。
